# 项目日报 - 2026-07-09

## 今日目标

- 明确 Mid360 和 RTK 未到货前仍可推进的软件任务。
- 建立后续可持续更新的项目日报机制。
- 按预硬件计划推进软件与仿真工作：传感器契约、TF 所有权、定位输入切换、坐标转换、Web 区域校验。

## 正在做的任务

- 自动割草机 ROS2 仿真与 Web 规划系统完善。
- 多区域、多障碍物覆盖路径规划稳定性验证。
- Web 前端、rosbridge、规划器、执行器的端到端流程梳理。
- Mid360 / RTK 未到货期间的软件推进计划执行。
- Web 区域 / 障碍物 payload 的后端校验和回归测试补强。

## 遇到的问题

- Mid360 LiDAR 和 RTK GPS 尚未到货，真实传感器数据、实机标定、RTK fix/float/single 状态、户外定位精度暂时无法验证。
- 硬件未到容易导致项目推进方向不清晰。
- 需要一个固定日报机制记录每天任务、问题、解决过程、完成项、卡点和下一步计划。
- Web 端区域 payload 如果为空、非法、自交、坐标格式错误或重名，存在清空旧有效任务、覆盖区域或生成歧义障碍物的风险。
- 启用 EKF 时，如果多个 launch 同时发布 `map -> odom`，可能造成 TF authority 重复。
- 前端、后端、仿真世界和 RTK/GPS 都依赖同一坐标原点，若不统一容易导致地图路径漂移。

## 解决过程

- 从产品经理视角拆分“硬件阻塞”和“软件可推进”两类工作。
- 确认硬件未到前仍可推进仿真闭环、坐标系契约、地图校验、任务状态机、安全逻辑、Mock RTK/Mid360、回归测试和演示流程。
- 制定并更新 `mid360-rtk-jiggly-nebula.md` 计划，明确先做仿真闭环、传感器契约、定位融合、Web 校验和硬件 bring-up 清单。
- 切换到以本地 `fix/web-launch-obstacle-planning` 为基线的新 worktree：`/home/yh/mower_ws/src/ROS2_sim_Fast-lio-worktrees/mid360-rtk-fixbase`。
- 先完成预硬件传感器契约：明确 `/velodyne_points`、`/imu/data`、`/gps/fix`、`/odom`、`/Odometry`、`/odom/gps`、`/odometry/filtered`、`/scan`、`/cmd_vel` 等软件接口。
- 修正 TF 所有权：保留 `hill_sim_launch.py` 负责 `map -> odom`，移除 `hill_ekf.launch.py` 中重复的 `map -> odom` 静态发布。
- 给 `multi_area_executor` 增加 `odom_topic` 参数：最小仿真默认 `/odom`，EKF 模式通过 `hill_full.launch.py` 切到 `/odometry/filtered`。
- 抽出 GPS/local 坐标转换模块 `geo_projection.py`，让后端复用统一的 `gps_to_local()` / `local_to_gps()`。
- 增加 `web_area_validation.py`，把 Web 区域 payload 的解析、坐标转换、命名校验、polygon 校验和障碍物归属从 ROS callback 中抽成纯函数。
- 改造 `multi_area_definer.web_areas_callback()`：只有存在有效条目时才替换当前任务，避免坏 payload 清空旧有效区域。
- 增加 helper 级和 callback 级回归测试，覆盖空 payload、自交 polygon、太小 polygon、坐标缺失/非数字、重复名称、区域内/外障碍物等场景。
- 增加区域/障碍物重叠检测：后出现的重叠区域或重叠障碍物被跳过并记录 warning；障碍物跨多个区域时跳过，避免归属歧义。
- 使用 TDD 流程：先写 failing test，确认失败，再实现最小逻辑，最后运行回归测试。
