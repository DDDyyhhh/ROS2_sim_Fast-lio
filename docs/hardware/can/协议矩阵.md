# RK3588 ↔ STM32 CAN 协议矩阵

来源：`RK3588_CAN协议手册.md` V1.0（2026-07-16）。本矩阵只整理已经交付的
上位机接口；没有 DBC、下位机源码或 `candump` 抓包可以互相校验，因此未定义的
字段不做推断。

## 总线和帧边界

| 项目 | 已确认值 |
| --- | --- |
| 总线 | 经典 CAN，不使用 CAN FD |
| 波特率 | 500 kbit/s |
| 标识符 | 11 位标准帧 |
| 控制帧 | `0x005`，DLC=8，RK3588 每 50 ms 发送完整帧 |
| 反馈帧 | `0x507`，DLC=8，STM32 约每 40 ms 发送 |
| 控制超时 | 连续超过约 500 ms 未收到控制帧时停车并进入安全锁定 |
| 应用层校验 | 无 CRC、序列号或应用层 ACK |

## RK3588 → STM32：`0x005`

| Byte | 字段 | 编码 | 已确认语义 |
| ---: | --- | --- | --- |
| 0 | `ctrl_mode` | `uint8`，仅 `0/1/2` | 退出 API / API 待机 / API 运行 |
| 1 | `vx_raw` | 二进制补码 `int8` | `vx_raw × 0.1 m/s`，推荐 `-10..10` |
| 2 | `vy_raw` | 二进制补码 `int8` | 差速底盘忽略；协议要求填 `0` |
| 3 | `omega_raw` | 二进制补码 `int8` | `omega_raw × 0.1 rad/s`；正负方向需现场标定 |
| 4 | `blade_level` | `uint8` | `0..3`，割刀挡位；下位机会钳位大于 3 的值 |
| 5 | `lifter_level` | `uint8` | `1..5`，刀盘高度挡位；下位机会钳位越界值 |
| 6 | `bag_target` | `uint8` | `0` 关闭草袋，非 `0` 打开草袋 |
| 7 | `magic_key` | `uint8` | 正常为 `0x00`；`0xAA` 仅用于明确的解锁操作 |

启动顺序：先发送 `ctrl_mode=1`，确认反馈 Byte4 为 `1`；再发送
`ctrl_mode=2`，确认反馈 Byte4 为 `2`；之后才允许发送非零速度。`0xAA` 不得
在普通 50 ms 控制帧中持续发送。

## STM32 → RK3588：`0x507`

| Byte | 字段 | 编码 | 已确认语义 |
| ---: | --- | --- | --- |
| 0–1 | `vx_feedback` | 大端 `int16` / 1000 | API 模式下为上位机速度指令回显，单位 m/s |
| 2–3 | `omega_feedback` | 大端 `int16` / 1000 | API 模式下为上位机角速度指令回显，单位 rad/s |
| 4 | `ctrl_mode` | `uint8`，`0/1/2` | 当前 API 状态 |
| 5 | `battery_soc` | `uint8` | BMS RSOC，正常为 0–100%；故障占位 `0x01` 有歧义 |
| 6 | `bms_temperature` | `uint8` | 摄氏度；`0xFF` 表示未知/异常 |
| 7 | `status_flags` | 位字段 | 见下表 |

### `status_flags`

| 位 | 掩码 | 语义 |
| ---: | ---: | --- |
| 0 | `0x01` | 草袋实际状态：1=打开 |
| 1 | `0x02` | 草袋连接：1=已连接 |
| 2 | `0x04` | 草袋满载：1=满载 |
| 3 | `0x08` | 保留，协议要求为 0 |
| 4–5 | `0x30` | 割刀挡位，右移 4 位 |
| 6–7 | `0xC0` | 保留，协议要求为 0 |

## 明确不接入的接口

- `0x508`、`0x509`：当前 OID 配置没有真实轮位置数据，不作为里程计。
- `0x506`：源码中存在旧状态帧函数，但手册确认当前没有调用点。
- OID 节点 `0x001..0x004`：STM32 内部电机总线协议，RK3588 不应直接发送。
- 未知 ID、CAN FD、远程帧和非 8 字节的本协议帧：离线解析时拒绝或跳过，不能
  当作已知协议使用。

## 当前仍需人工/现场确认

- `omega` 正负方向和车体坐标系的现场标定。
- 急停、碰撞、遥控器接管后的解锁责任和完整操作流程。
- 没有故障码、锁定原因和命令 ACK 时，如何把反馈不足映射到产品层错误提示。
- `can0/can1` 的实际物理归属、总线终端和伙伴方案的控制权 owner。

本阶段只提供纯 Python 离线解码和 `candump -L` 回放，不打开 SocketCAN、不发送
任何帧、不接入 ROS `/cmd_vel`。带时间戳的回放还会审计 `1 → 2` 启动握手、反馈
确认后才允许非零速度、500 ms 控制帧超时和连续 `0xAA` 解锁键。由于 `0x507` 没有
碰撞、急停、遥控器接管或锁定原因字段，离线审计不能证明这些物理事件是否发生。
